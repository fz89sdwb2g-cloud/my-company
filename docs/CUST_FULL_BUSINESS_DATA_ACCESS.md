# Повний доступ до бізнес-даних КУСТ без персональних даних людей
Завдання для розробника КУСТ від власника бізнесу. Дата: 14.11.2026.

## Мета та межі
Надати інтеграції «Моя компанія» повну операційну й фінансову картину за всіма точками обліку. Не обмежуватися поточною версією API з чеками та залишками. Доступ до КУСТ — лише читання. Дані людей, секрети й довільний текст не передавати.

Це завдання на розширення джерела, а не повідомлення про вже наданий доступ. Зміни мають бути реалізовані на стороні КУСТ. Права в Supabase або в програмі «Моя компанія» не розширюють джерело КУСТ.

## Які дані передавати

| Група | Потрібні дані |
|---|---|
| Довідники | Коди фактичних точок, їх облікове охоплення, товари й категорії, базові одиниці та перерахунок упаковок |
| Продажі й повернення | Проведені документи, дати, статуси, суми після знижок, собівартість, тип продаж/повернення; зв’язок повернення з продажем |
| Оплати | Суми, дати, способи оплати та знеособлені зв’язки з документами; часткові оплати, погашення боргів, аванси й переплати окремо |
| Борги клієнтів | Початкові й поточні непогашені залишки за документами/кодами клієнтів, суми оплат і коригувань, погоджені строки та дати передачі товару; включно з боргами минулих періодів |
| Борги постачальникам | Окремий напрям розрахунків: суми, дати виникнення, строки, оплати й залишки за кодами контрагентів |
| Каси й банк | Залишки на дату, початкові залишки, надходження, видатки та внутрішні переміщення. Спільна каса магазинів і каса складу — окремо. Банківські рахунки — лише знеособлені коди й залишки |
| Закупівлі | Проведені надходження, повернення постачальникам, суми, собівартість, кількість і оплати, зв’язки з товарами та точками |
| Фізичні запаси | Кількість і вартість товару на кожній точці, метод оцінки, рухи: надходження, продаж, повернення, переміщення, списання, коригування |
| Витрати | Проведені суми за категоріями: оренда, доставка, реклама, комісії, податки, комунальні та інші наявні витрати. Оплата праці — агреговано, без даних окремих людей |
| Доставка, оренда, послуги | Фінансові суми, статуси, дати й зв’язки з документами; без імен, адрес та вільних приміток |
| Прибутковість | Показники й вихідні суми для валового та чистого прибутку з описаною методикою, датою й ознакою повноти обліку |

За відсутності певних даних у КУСТ явно повернути «не ведеться» або «неповне джерело». Не підставляти нулі й не обіцяти розрахунок чистого прибутку без повного обліку витрат.

## Захист персональних даних на стороні джерела
Використати дозволені поля та підготовлені представлення/експорт. Виключення виконувати ДО передачі даних інтеграції, а не лише приховувати в інтерфейсі.

Не передавати:
- ПІБ клієнтів, майстрів, працівників та інших фізичних осіб;
- телефони, email, адреси доставки/проживання;
- документи, податкові ідентифікатори фізичних осіб, банківські реквізити, IBAN, карткові дані;
- паролі, хеші паролів, токени, ключі, секрети ПРРО, IP та технічні журнали;
- вільні примітки, коментарі, вкладення й довільні документи за замовчуванням.

Для фінансових зв’язків повертати стабільні непрозорі коди клієнтів/майстрів/контрагентів. Не передавати таблицю відповідності цих кодів особам. Коди однакові в документах, оплатах, поверненнях і боргах. Секрети автентифікації передавати лише через погоджений захищений механізм, не всередині бізнес-відповідей, URL або журналів.

## Важливі визначення
1. Касове надходження не дорівнює виручці: воно може містити погашення боргу, аванс або переказ.
2. Виручка не дорівнює прибутку; вартість запасів не дорівнює грошам у касі.
3. Непогашений борг має збігатися зі звітом КУСТ після всіх оплат, повернень і коригувань. Поле debt без перевірки його змісту не є достатнім.
4. Прострочення: погоджений строк має пріоритет; інакше 14 календарних днів після передачі товару. Прострочення починається наступного дня після строку за Europe/Kyiv. Без обох дат строк невідомий, а не автоматично прострочений.
5. Не віднімати переплати одного клієнта від боргів іншого; переплати й аванси показувати окремо.
6. Обов’язково передавати ознаку типу позиції: фізичний товар, код палітри/тонування, доставка, оренда, інша послуга. Нетоварні позиції не входять до вартості фізичних запасів. Не визначати тип за кількістю 100, лише за назвою чи ціною.
7. Якщо два магазини мають один код обліку, повернути спільну точку й явно описати її охоплення; не створювати вигаданий поділ.

## Спосіб передачі
Розробник може розширити чинний захищений API або надати еквівалентний регулярний очищений експорт. У будь-якому варіанті:
- окремий відкличний доступ лише для читання й лише до погоджених бізнес-полів;
- актуальні залишки та доступна історія для обраних періодів, включно з початковими боргами й залишками;
- стабільні коди документів, ознаки проведення/скасування та опис змісту полів;
- гроші — десяткові рядки з валютою, дати/час — з визначеним Europe/Kyiv;
- узгоджений знімок: snapshot_id, data_as_of, complete; усі сторінки/файли без пропусків і дублів;
- контрольні підсумки для звірки кожної групи, перелік доступних і відсутніх груп;
- недоступність джерела відрізняється від коректного нульового залишку;
- щоденна доступність свіжих даних для оновлення о 07:00 за Києвом. Вхід поновлювати під час кожного запуску; чинний токін живе одну годину.

## Перевірка й передача
1. Погодити склад і значення полів без персональних даних.
2. Передати точні адреси/формат джерела, правила авторизації, пагінації та доступні групи.
3. На однаковий час звірити з робочими звітами КУСТ: борги, прострочення, каси/банк, продажі, закупівлі та фізичні залишки.
4. Перевірити часткову оплату, погашення старого боргу, повернення, аванс, переплату, внутрішній переказ, послугу з умовною кількістю та відсутність дати.
5. Підключати до панелі кожну групу після окремої перевірки. При збої не перезаписувати попередній перевірений результат.

Очікуваний результат: власник один раз погоджує повний склад доступу; інтеграція отримує всі потрібні бізнес-дані без персональних даних. Подальше заповнення й звірку панелі виконує асистент, без ручного перенесення кодів користувачем.
