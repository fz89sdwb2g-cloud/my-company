# КУСТ: доповнити API чеками, оплатами та боргами
**Володі від Любомира · 16.11.2026**

Володю, попередній опис був надто загальний. Зараз потрібне конкретне доповнення до API, яке ти вже зробив:
`https://svi.ber.te.ua/cust/servise/api/v1`.

**Завдання: розширити GET /receipts і додати GET /receivables. Авторизацію POST /login та існуючі ендпойнти залишити сумісними.** Нижче — запропоновані назви нових полів. Якщо відповідні поля вже є під іншими назвами, достатньо передати їх і написати відповідність.

## 1. GET /receipts — чеки з рядками, оплатами та борговим статусом
Зараз ми отримуємо чек, дату, точку, тип та загальну суму. Потрібні також:
- `receipt_id`, `location_id`, `business_date`, `occurred_at`, `updated_at`, `type`, `currency`, `total` — зберегти наявні поля/значення; пояснити типи й знаки повернень.
- `document_status` — проведений / скасований / інший фактичний статус; не змішувати скасовані чеки з продажами.
- `customer_id` — стабільний знеособлений код клієнта.
- `is_debt_marked` — саме ознака, за якою чек у КУСТ позначається червоним/борговим. Коротко пояснити правило; не визначати його лише за кольором.
- `paid_amount` — зараховані оплати; `debt_balance` — поточний непогашений борг за чеком з урахуванням оплат, повернень і коригувань.
- `due_date` — обліковий строк оплати або null; `delivered_at` — дата передачі товару, якщо ведеться, інакше null. Не вигадувати дати.
- `original_receipt_id` — зв’язок повернення з первинним чеком, якщо він є.
- `items[]`: код рядка, `product_id`, назва товару, одиниця, кількість, ціна, знижка, сума рядка, собівартість реалізації — де вона реально є. Для типу позиції: товар / палітра / доставка / послуга / невідомо.
- `payments[]`: стабільний `payment_id`, дата, сума, валюта, вид оплати, знеособлений код каси/рахунку, сума цієї оплати, зарахована саме на цей чек. Повернення оплати й сторнування мають відрізнятися від надходження.

**Важливо:** борговий чек може мати часткову оплату; погашення старого чека не є новим продажем. Одна оплата може покривати кілька чеків — не дублювати всю оплату в кожному, передавати розподілену суму.

Зберегти чинні `from`, `to`, `location_id`, `limit`, `cursor` і формат `{data:[], meta:{...}}`. Явно вказати, за якою датою працює фільтр; зберегти поточну сумісність дат і пагінації. Потрібне читання всіх фактичних точок, включно зі складом, якщо продажі там ведуться. Якщо магазини мають спільний облік — так і передавати.

## 2. GET /receivables — повний поточний залишок клієнтських боргів
Це **знімок усіх відкритих боргів на момент запиту**, незалежно від дати продажу. Чеки минулих місяців і років та початкові борги теж включити. Фільтр поточного місяця тут не застосовувати.

Параметри: `location_id` (необов’язковий; без нього всі точки), `limit`, `cursor`.

На кожен борг:
- `debt_id` — стабільний код;
- `receipt_id` — код пов’язаного чека або null для початкового боргу без чека;
- `customer_id` — той самий знеособлений код, що в чеках;
- `location_id` — фактична точка або null, якщо не визначена;
- `origin` — чек / початковий борг / інше;
- `business_date`, `due_date`, `delivered_at`, `updated_at` — наявні дати, відсутні null;
- `debt_balance`, `currency` — фактична непогашена сума;
- `is_debt_marked` — облікова боргова ознака, якщо застосовна.

Якщо борг ведеться загально по клієнту і не розподілений на чеки, передати його окремим записом з `receipt_id:null` і пояснити це. **Не дублювати ту саму суму одночасно як борг клієнта та борги його чеків.**

Аванси/переплати передати окремо, якщо вони є: не віднімати переплату одного клієнта від боргу іншого. Можна окремим масивом у відповіді; описати його.

Пропонований приклад відповіді — суми й коди нижче вигадані:
```json
{
  "data": [
    {
      "debt_id": "debt-example",
      "receipt_id": "receipt-example",
      "customer_id": "customer-example",
      "location_id": "loc-01",
      "origin": "receipt",
      "business_date": "2026-10-20",
      "due_date": null,
      "delivered_at": null,
      "updated_at": "2026-11-16T06:00:00Z",
      "debt_balance": "750.00",
      "currency": "UAH",
      "is_debt_marked": true
    }
  ],
  "meta": {
    "snapshot_id": "snapshot-example",
    "as_of": "2026-11-16T06:00:00Z",
    "next_cursor": null,
    "complete": true
  }
}
```
Усі сторінки одного знімка мають узгоджені суми й дату. Написати, як отримати наступну сторінку без пропусків. Якщо знімки не підтримуються — вказати фактичне обмеження. Помилку не повертати як успішний порожній список.

## 3. Без персональних даних, лише читання
Не передавати ПІБ, телефони, email, адреси, податкові/паспортні коди, банківські реквізити, вільні примітки та секрети. Клієнтів позначити стабільними непрозорими кодами, без таблиці відповідності людям. Службові ID чеків, товарів, оплат і боргів залишити — вони потрібні для зв’язків і усунення дублів.

Токен отримуватимемо через чинний /login при кожному запуску; зараз строк його життя 3600 секунд. Логіни, паролі та токени не записувати в діагностичні журнали й приклади відповідей. КУСТ з нашого боку тільки читаємо.

## 4. Що передати після виконання
1. URL і приклад запиту до кожного доповненого ендпойнта; короткий опис полів, дат, статусів і пагінації. За потреби — очищений приклад JSON.
2. Перевірити три випадки: неоплачений борговий чек; частково оплачений; старий чек, борг якого вже повністю погашений (у списку відкритих боргів його немає).
3. На одну дату звірити кількість відкритих боргів і загальну суму з відповідним звітом КУСТ. Якщо «червоний чек» і відкритий борг — різні ознаки, прямо пояснити різницю.
4. Вказати недоступні поля й початок доступної історії. Відсутні суми не підміняти нулями.

**Не потрібно робити екрани, графіки або фінансову аналітику нашої програми. Достатньо цих даних і короткого пояснення — інтеграцію, перевірки та відображення зробимо ми. Окремий експорт усієї бази для цього завдання не потрібен.**

Інші групи з попереднього широкого запиту (каси, закупівлі, витрати тощо) зараз не є умовою завершення саме цього завдання. Цей документ конкретизує поточний крок: чеки, їхні оплати та клієнтські борги.
